---
name: Orval api-zod barrel collision
description: Why lib/api-spec orval zod output uses indexFiles:false and a hand-written index.ts
---

The zod orval output (`lib/api-spec/orval.config.ts`) generates:
- `lib/api-zod/src/generated/api.ts` — zod schema **values** (`export const CreateSubscriberBody = zod.object(...)`)
- `lib/api-zod/src/generated/types/*` — TS **interfaces** with the same names (`export interface CreateSubscriberBody`)

By default orval also (re)writes the root `lib/api-zod/src/index.ts` barrel to re-export BOTH
`./generated/api` and `./generated/types`. Because the schema value and the model interface share
names (e.g. `CreateSubscriberBody`, `UpdateVoucherBody`), the double `export *` triggers
`TS2308: Module "./generated/api" has already exported a member named 'X'`.

**Why it can appear "suddenly":** the committed `index.ts` may be stale (generated by an older orval
that didn't emit the types line). Any fresh `pnpm --filter @workspace/api-spec run codegen` in the
current environment reintroduces it, so it looks like a new task caused it when it's latent.

**Fix (in place):** `indexFiles: false` on the zod `output` block so orval stops regenerating the
barrel, plus a hand-written `lib/api-zod/src/index.ts` containing only `export * from "./generated/api";`.
Consumers only use the zod schema **values** (server `.safeParse`), so the TS interfaces don't need
re-exporting. `export type * from "./generated/types"` does NOT fix it — it just flips the collision.

**How to apply:** never restore orval's default index generation for the zod output; if codegen ever
overwrites `index.ts` again, re-check that `indexFiles: false` is still present.
