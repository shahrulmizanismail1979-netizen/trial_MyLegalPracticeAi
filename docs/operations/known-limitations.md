# Known-Limitations Register — Judgment Research Platform

**Last updated:** 2026-07-30  
**Purpose:** Honest record of confirmed limitations at this release. Each limitation has a mitigation, an owner, and a target resolution date or condition.

---

## Security Limitations

### KL-01 — Upload Submitter Binding Incomplete (Task #7 open)

**What:** Upload routes do not currently bind a container to the staff member who uploaded it. An authenticated staff member with an operational role (owner, administrator, rights_reviewer) can access containers uploaded by another staff member before the rights decision is complete.

**Impact:** Within the authenticated staff cohort, there is no ownership-based access control on pre-rights-review containers. The rights model (UNREVIEWED → restricted to rights roles) provides a partial mitigation, but the ownership check itself is missing.

**Mitigation:** All routes require staff authentication. Rights model caps access to UNREVIEWED containers at rights-privileged roles only. Audit trail records all access.

**Resolution:** Task #7 — Stop unauthorized document access by binding uploads to their submitter.

**Owner:** Developer  
**Target:** Before READY_FOR_LIMITED_INTERNAL_PILOT

---

### KL-02 — Cross-Subscriber Chat Isolation Not Formally Verified (Task #21 open)

**What:** The isolation between AI chat sessions belonging to different corporate subscribers has not been formally verified under future schema changes. The concern is that future modifications could inadvertently create a cross-subscriber data path.

**Impact:** Current implementation appears isolated, but the absence of a formal verification or regression test means this cannot be asserted with confidence.

**Mitigation:** Chat routes require individual Clerk session authentication. Sessions are scoped to individual accounts.

**Resolution:** Task #21 — Make sure corp subscribers can't read each other's AI chats after future changes.

**Owner:** Developer  
**Target:** Before READY_FOR_LIMITED_INTERNAL_PILOT

---

### KL-03 — Job-Stealing Test Coverage Gap (Task #87 open)

**What:** There is no automated test confirming that two parallel job workers cannot simultaneously claim and process the same job (job-stealing). The database-level `FOR UPDATE SKIP LOCKED` claim mechanism is designed to prevent this, but the correctness under concurrent load has not been adversarially tested.

**Impact:** In the current single-worker production configuration, this is not an active risk. If parallel processing is introduced, undetected job-stealing could lead to duplicate processing.

**Mitigation:** `FOR UPDATE SKIP LOCKED` is the standard PostgreSQL mechanism for contention-free queue claiming. No parallel workers in current production.

**Resolution:** Task #87 — Confirm job-stealing between parallel test workers can't happen silently.

**Owner:** Developer  
**Target:** Before introducing parallel job processing

## Data and Processing Limitations

### KL-04 — OCR Confidence Threshold Not Calibrated to Real Corpus

**What:** The OCR review threshold of 70% mean confidence was set based on synthetic fixture testing. It has not been calibrated against a representative sample of real Malaysian court documents.

**Impact:** On real corpus documents, the threshold may be too permissive (passing low-quality OCR without review) or too conservative (routing acceptable OCR to human review unnecessarily).

**Mitigation:** Low-confidence pages are routed to human review rather than silently accepted. Human reviewers can correct OCR output via append-only corrections.

**Resolution:** Run OCR quality assessment on the first real-corpus batch and adjust the threshold via an ADR.

**Owner:** Developer  
**Target:** After first full-corpus batch

---

### KL-05 — Pilot Not Run With Court-Issued Documents

**What:** The Phase 14 pilot was run with synthetic PDF documents generated by the pilot corpus generator script (`generate-pilot-corpus.ts`), not with actual court-issued judgment files. The acceptance gate passed on the synthetic corpus.

**Impact:** Processing behaviour on real court documents (varying formatting, scan quality, editorial conventions, language mixing) may differ from synthetic fixtures.

**Mitigation:** The pilot confirmed the pipeline mechanics (upload, rights, extraction, segmentation, cross-file detection, audit trail). The segmentation engine uses deterministic heuristics trained on Malaysian legal text patterns in synthetic fixtures.

**Resolution:** Human-reviewer sign-off on a real-document pilot batch is required before corpus import.

**Owner:** Rights reviewer / Legal reviewer  
**Target:** Before full-corpus import

---

### KL-06 — Full-Corpus Performance Unverified at Scale

**What:** The stress test suite (`stress.test.ts`) exercises the platform with a synthetic corpus, but performance at the target full-corpus scale (hundreds of containers, thousands of candidates, concurrent rights decisions) has not been formally benchmarked.

**Impact:** The platform may be slower than acceptable or may encounter database connection limits at scale.

**Mitigation:** Job queue is database-backed and designed for sequential processing; the design explicitly supports future replacement with an external queue. Stress test provides a partial baseline.

**Resolution:** Formal capacity test with production-representative data before full-corpus import.

**Owner:** Developer  
**Target:** Before full-corpus import

---

### KL-07 — AI Evidence Not Enabled by Default

**What:** The AI evidence layer (Phase 10 — headnotes, case analysis, AI propositions) is implemented but disabled by default. `isEnabled()` returns false. No data flows to any AI provider.

**Impact:** AI-assisted research features are unavailable until explicitly enabled via an ADR and configuration change.

**Mitigation:** Disabling AI is a deliberate security and rights-compliance decision. Enabling it requires a formal ADR recording which provider, which data, and what rights restrictions apply.

**Resolution:** To be enabled via a future ADR when the rights framework for external AI submission is established.

**Owner:** Platform owner  
**Target:** Future phase

## Operational Limitations

### KL-08 — No Automated Backup Verification

**What:** Database backups are taken manually following the backup-and-restoration.md procedure. There is no automated backup schedule or automated restoration test.

**Impact:** A backup taken but not verified may be corrupt. A missed backup means data loss up to the time since the last manual backup.

**Mitigation:** Manual backup procedure documented. Recommendation to take backups before major operations (imports, migrations).

**Resolution:** Implement automated backup with automated restoration verification.

**Owner:** Administrator  
**Target:** 2026-09-30

---

### KL-09 — Object Storage Not Independently Backed Up

**What:** The private object storage bucket containing original uploaded files and page images is not covered by an independent backup procedure. If the Replit object storage service loses data, original files cannot be recovered from a platform backup.

**Impact:** Loss of original uploaded documents (the canonical source for all derived data). Database records would remain but would reference missing files.

**Mitigation:** Original files are stored in Replit's managed object storage, which has its own infrastructure durability. Containers whose storage keys are missing are quarantined during the restoration verification process.

**Resolution:** Implement an independent object storage backup to a separate storage provider.

**Owner:** Administrator  
**Target:** 2026-09-30

---

### KL-10 — No SLA Commitments

**What:** No formal service-level agreement exists for the platform. There are no commitments on availability, response time, or recovery objectives beyond the targets in backup-and-restoration.md (RTO 4 hours, RPO 24 hours).

**Impact:** Users have no contractual basis for expecting availability.

**Resolution:** Define and agree SLA when the platform reaches READY_FOR_CONTROLLED_PRIVATE_USE.

**Owner:** Platform owner  
**Target:** Before READY_FOR_CONTROLLED_PRIVATE_USE

---

### KL-11 — Human-Review Time Not Measured

**What:** The pilot report (§12) records that human-review time has not yet been measured. There is no established benchmark for how long rights review, segmentation review, and judgment verification take per container.

**Impact:** Capacity planning for operational rollout is difficult without time-per-container benchmarks.

**Resolution:** Measure review time during the first real-document pilot batch.

**Owner:** Rights reviewer / Administrator  
**Target:** During first real-document pilot
